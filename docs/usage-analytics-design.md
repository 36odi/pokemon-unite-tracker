# 利用規模を知るための簡易計測設計

改訂日：2026-10-06（JST）、設計v4.2。v4.1の簡易案を維持し、UUID列型と権限エラーの確認条件だけを補足。
状態：ローカル実装と隔離テスト済み（v5.60 / SW v86）。本番DBへの適用は未実施。ユーザー指示によりpush対象。公開結果はGit履歴・配信状態を参照。利用数の記録開始には専用テーブルの追加が必要。

## 1. 目的と分かること

目的は、個人運営のサイトを「だいたいどれくらいの人が使っているか」知ること。商業分析や利用者別の行動分析は行わない。

主な指標は **「直近30日に機能を使ったブラウザ数」** とする。ランダムIDは端末そのものではなく、ブラウザの保存領域を識別する。同じ人の複数端末や保存領域の消去は重複し、共有ブラウザは複数人でも1つになる。正確な実人数とは呼ばない。

PostHog、アカウントとの関連付け、機能別・ログイン状態別の内訳は採用しない。GoatCounterは既存の訪問計測だけを維持する。

## 2. 数える条件と保存内容

本人の操作によって「対戦記録の保存」「分析・ラボの有効な結果表示」「メダル編集・保存」のいずれかが成功した日に記録する。ページを開いただけ、初期表示、自動復元、空の結果、保存失敗、クラウド移行は数えない。閲覧時間は測らない。

既存Supabaseプロジェクトに、計測専用テーブルを1つ追加する。

| 列 | 内容 |
|---|---|
| `browser_id` | DBの列型は`uuid`。解析専用のランダムUUIDをブラウザ内に保存し、再訪でも使う。UUIDとして不正な値はDBで拒否する |
| `used_on` | DBの列型は`date`。初期値を`(now() AT TIME ZONE 'Asia/Tokyo')::date`とするJSTの日付。操作の詳細時刻は保存しない |

同じID・同じ日付の組を複合主キーとして1行だけにする。他の独自の一意制約は設けない。アカウントID、ログイン状態、機能名、対戦記録、メール等を列に持たず、既存ユーザーテーブルとも結合しない。

## 3. 送信の最小構成

- 該当操作の成功後、解析専用の小さな共通処理を呼ぶ。PostHog用SDKや追加サービスは不要。
- 普通の追加（INSERT）で送り、重複時の更新・無視を指定するupsertは使わない。返却は`return=minimal`とし、行を返す指定や`.select()`を付けない。複合主キーの重複エラー`23505`は「記録済み」として扱う。HTTP 409だけで成功判定しない。権限不足・通信失敗等は記録済みにしない。
- 成功または上記の重複確認が済んだ日は以後の送信を省く。送信済み日付の判定も`Asia/Tokyo`を明示してJSTに揃え、送信開始時の日付を使う。UTCの`toISOString().slice(0,10)`や端末設定の日付で代用しない。端末のタイムゾーン差は除けるが、端末時計自体のずれは残る。
- 既存のログイン済み`db`クライアントを送信に使わない。ログイン情報を持たない直接のAPI送信を使い、公開用キーだけで書き込む。利用者のアクセストークンや認証Cookieを付けず、参照元URLも送らない。
- 日付はDBで決め、ブラウザに任意の日付の書き込み権限を与えない。ブラウザIDはアカウント削除やログアウトで作り直さない。
- IDを保存できない、計測停止中、運営・ローカル・プレビューの操作は送信しない。
- オフラインの操作を独自キューに残さない。送信失敗をその日の成功として記録せず、後の該当操作で再試行する。解析の失敗は保存・表示を妨げない。

公開キーだけで送っても、既存クライアントが利用者の認証情報を付ければアカウントと関連し得る。保存列と通信の両方で関連付けを避ける。[Supabase APIキーと認証の区別](https://supabase.com/docs/guides/getting-started/api-keys)

対象列を指定する`ON CONFLICT`は、その列のSELECT権限を要求する。すべての重複無視が必ず失敗するという意味ではないが、この設計は普通のINSERTで揃える。`23505`はHTTP 409に対応し、別のエラーも409になり得る。[PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html)・[PostgRESTエラー](https://docs.postgrest.org/en/stable/references/errors.html)

## 4. 閲覧権限と集計

RLSを有効にする。新規の計測テーブルに限り、`PUBLIC`・`anon`・`authenticated`の既存のテーブル／列権限を外し、`anon`に`INSERT(browser_id)`だけを許可する。RLSの追加許可も`anon`に限定する。`used_on`のINSERT権限は与えず、送信本文にも含めない。テーブル全体のINSERT権限が残っていると、列権限の制限だけでは防げない。既存の対戦記録等の権限は変更しない。[PostgreSQL GRANT](https://www.postgresql.org/docs/current/sql-grant.html)

公開・ログイン済み利用者からの読取・更新・削除は許可せず、結果行も返さない。一般利用者から呼べる人数集計APIは作らず、運営者がSupabaseのSQL画面で確認する。管理キーをアプリに入れない。[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

権限不足の`42501`は、利用者の認証情報を付けない送信ではHTTP 401、認証済みの送信では403に対応する。拒否の確認を403だけに固定せず、エラーコードと認証条件を確認する。401を重複・記録済みとは扱わない。[PostgRESTエラー](https://docs.postgrest.org/en/stable/references/errors.html)

集計は、今日を含むJSTの直近30日間にある`browser_id`の重複を除いた件数。今日の分は途中経過で、導入直後は「計測開始からN日間」と表示する。日別人数を足して30日人数にしない。集計時に30日より古い計測行を管理側のSQLで削除する。確認の間隔によって保存期間は30日を超えるので、30日で必ず自動削除されるとは案内しない。

推移を見たいときは、確認のたびに「集計日・対象期間・ブラウザ数」を運営者のメモに残す。元のID別記録は30日案のままとし、約13か月への延長は今回選択していない。削除した期間を後から集計し直すことはできない。

公開書込は、不正なIDによる水増しまで防げる仕組みではない。通信遮断・オフラインによる欠測率も分からないため、値は利用規模の参考とする。「JS20行」「何年も放置可能」という実装量・保守の保証はしない。

## 5. 利用者への説明

推奨候補は、内容を案内して計測を初期有効にし、設定から停止できる方式。既存Supabaseを使うため新しいサービス事業者は増えないが、新しい利用目的の通信は増える。非商業利用、ランダムID、既存送信先という理由だけで法的な扱いが解決したとはしない。

実装した案内文：「登録せずに使っている方も含め、このツールがどれくらい利用されているかを知るため、利用状況を計測しています。今回の計測では、氏名やメールアドレスは収集しません。利用規模の集計に使うのは、利用した日と、同じブラウザを重複して数えないためのランダムな番号です。ログインアカウントとは結び付けず、計測のために対戦記録を送ることもありません。計測は下の設定でいつでも停止できます。停止しても、すべての機能をそのまま使えます。」

停止設定は維持し、表示名は「利用状況の計測」「画面の訪問数の計測」とする。初期有効・ブラウザ単位の設定であることは常時表示。保存先・30日集計・古い記録の削除は、同じ画面の「詳しい内容」に掲載する。Supabase側のアクセス記録は計測案内から外し、ログイン前とアプリ下部の「データの扱いについて」にまとめる。「個人情報を一切収集しない」とは断言しない。

Supabaseの公式仕様では、APIへのアクセスはログの対象で、接続日時・IPアドレス・User-Agent・接続先・応答状態等が記録項目に含まれる。全項目がすべての通信で埋まるとは限らず、保存期間は契約プランに依存する。今回のプロジェクトの実ログ・保存期間は未確認。「データの扱いについて」では、サービス側にアクセス記録が残ること、これらを利用規模の集計には使わないこと、計測を停止してもログインや記録の保存等に必要な通信は続くことを説明する。計測表の古い行を削除しても、サービス側のログ削除を意味しない。[Supabaseの記録項目](https://supabase.com/docs/guides/observability/log-field-reference)・[ログと保存期間](https://supabase.com/docs/guides/observability/logs)

これは案内の草案であり、「1文あれば法的に十分」という判定ではない。IP等が通信先のログに残る可能性もあるため、完全匿名とは説明しない。送信先・内容・目的・保管と削除の運用・停止方法を既存の案内に具体的に記載する。停止は既存対戦記録を消さず、GoatCounterの扱いも区別して説明する。

## 6. 実装時に確認すること

| 確認 | 期待結果 |
|---|---|
| 同じブラウザで同日・翌日に使う | 同日は1行、翌日は別行。30日集計では1ブラウザ |
| 同じID・同じ日に通常追加を繰り返す | `23505`だけを記録済み扱い。行を返さず、他の409や権限エラーは成功扱いしない |
| UUIDとして不正なIDを追加する | DB側で拒否され、計測行が増えない |
| 初期表示・失敗・自動処理 | 計測行を追加しない |
| ログイン状態で送信する | 通信に利用者の認証情報がなく、アカウントと結び付ける列・処理もない |
| 公開・ログイン済み利用者が計測表を読む／変更する | 読取・更新・削除ができない。`42501`は利用者認証なしなら401、認証ありなら403を想定。追加は指定した匿名送信だけ |
| 送信本文に任意の日付を含める | 列権限で拒否される。日付を省いた正しい追加にはDB側のJST日付が付く |
| 停止・オフライン・送信失敗 | アプリは使える。停止中は送信せず、失敗を成功済みにしない |
| 運営除外・海外タイムゾーンの端末・JST境界・30日集計 | 運営分を除外し、日付と重複排除が定義どおり。送信中に日付が変わっても翌日分を省かない |

ローカル検証：共通処理32項目、検証用PostgreSQLの権限・集計15項目、Edgeの操作・通信41項目が通過。ブラウザ検証はすべての通信を模擬し、本番送信は0件。PostgRESTを含む本番APIでの応答確認、実端末での日付越え・複数タブ同時送信は未実施。重複制約と日付越えの処理はそれぞれDB／共通処理の試験で確認した。

## 7. 導入と確認手順

1. 公開前に、運営者のブラウザを除外する。本番サイトを開いた状態の開発者用コンソールで `localStorage.setItem('usage_excluded','1')` を実行して再読込する。このブラウザでは簡易計測とGoatCounterの両方を停止する。別端末・別ブラウザにも設定する。
2. SupabaseのSQL Editorで [専用テーブル作成SQL](sql/usage-analytics-create.sql) を1回実行する。既存の対戦記録には触れない。同名テーブルが既にある場合は中断するので、内容を確認せず再利用しない。
3. アプリを公開し、専用の検証用ブラウザで操作後の通信・追加を確認する。利用者の認証情報なし、本文は `browser_id` だけ、返却行なしを確認する。本番環境の読取・日付指定等の拒否確認は、承認された検証として別途行う。
4. 人数を見たいときに [30日集計SQL](sql/usage-analytics-count.sql) を実行する。`active_browsers` がブラウザ数。`counted_at`・`period_start`・`period_end` と一緒にメモする。開始から30日未満は、計測開始日も添える。
5. 集計SQL末尾のコメントになっている削除文を、集計をメモした後に別途実行する。削除対象は30日より古い計測行だけ。定期削除は自動化していない。

利用者の停止設定は、ログイン前の画面とメニューの「利用状況の計測について・設定」にある。GoatCounterの訪問計測とは別々に停止できる。停止はこのブラウザ単位で、設定を消去すると初期有効に戻る。

再検証用ファイル：`tests/usage-analytics.test.js`、`tests/usage-analytics.browser.test.js`、`tests/usage-analytics.sql.test.js`。ブラウザ試験は既存テストと同じPlaywright／Edgeを使用。SQL試験だけはテスト用の `@electric-sql/pglite@0.3.14` を使い、`PGLITE_MODULE` にその場所を指定する。アプリへの追加依存はない。
